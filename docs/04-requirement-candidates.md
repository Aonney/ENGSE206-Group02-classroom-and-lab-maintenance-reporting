## 1. How We Turned Evidence into Requirement Candidates

หลักคิดของทีม:

1. เริ่มจาก Evidence ที่มี Evidence ID (E-ID)
2. วิเคราะห์ความต้องการ (Need) ของ Stakeholder จากหลักฐาน
3. แปลง Need เป็น Candidate Requirement ของระบบ
4. กำหนดสถานะเป็น `Candidate` หรือ `Needs Validation`
5. ระบุประเด็นที่ยังต้องตรวจสอบเพิ่มเติม (Follow-up)

# 3. Why These Are Candidates, Not Final Requirements

| RC | เหตุผลที่ยังไม่เป็น Requirement สุดท้าย |
|---|---|
| RC-F-03 | ยังไม่ทราบเกณฑ์ที่ใช้กำหนดว่างานใดเป็นงานเร่งด่วน (Urgent) |
| RC-F-05 | ยังไม่ยืนยันว่าใครเป็นผู้รับผิดชอบในการปิดงานและยืนยันการซ่อม และยังไม่มี Evidence E-ID ใน Evidence Log รองรับโดยตรง (มาจาก Negotiation N-03 เท่านั้น) |
| RC-F-06 | ยังไม่มีข้อสรุปว่าจะจัดการกรณีแจ้งปัญหาซ้ำอย่างไร |
| RC-F-07 | ยังต้องศึกษาการติดตามงานเมื่อมีการส่งต่อหลายหน่วยงาน |
| RC-F-08 | ยังต้องยืนยันประเภทของรายงานและสถิติที่ผู้บริหารต้องการ |

# 5. Student Takeaway

Requirement Candidate ที่ดีควรสามารถอธิบายได้ว่า

- อ้างอิงมาจาก Evidence (E-ID) ใด
- ตอบสนองความต้องการ (Need) ของ Stakeholder ใด
- ยังมีข้อมูลใดที่ต้องตรวจสอบเพิ่มเติม
- จะนำไปตรวจสอบและปรับปรุงใน Week 05 อย่างไร
